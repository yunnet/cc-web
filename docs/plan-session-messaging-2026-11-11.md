# 会话间派活 / 传消息：交互方案（草案，待用户决定）

来源：会话「采购公告要展示公告标题」的需求（2026-11-11），用户评价该功能"很好"、点名要做。

## 1. 现状

- 会话之间传消息是 **Claude Code 自己的功能**（SendMessage / ListAgents，本机经命名管道送达）。cc-web 目前完全不知道它：消息、被扣住、批准，全都只出现在各自标签页的终端里。
- 要让网页看见，只能在每个由 cc-web 启动的 Claude 里加载一个 mod（Claude Code 的插件钩子）。查了本机 2.1.319 的 mod 接口：

| 能做到 | 接口 |
|---|---|
| 看到**发出**的消息：发给谁、全文、是否送达、送不到的原因 | `session.send`（可改写正文） |
| 看到**收到**的消息：全文、来源是另一个会话 | `session.receive`（在排队前触发，可改写正文） |
| 知道接收方**开始处理**这条消息 | `prompt.submit`，`origin.kind = 'peer'`；被扣住的消息批准后才会走到这一步 |
| 知道接收方**处理完、空闲** | 已有的 `Stop` 钩子 |
| **做不到**：直接读"被扣住"状态，或从外部替接收方批准 | 接口里没有。批准只能在接收方终端里按键 |

- 仓库里提过的 ccweb-companion mod（CLA-18 网页权限卡片）现在本机已经没有安装，等于从零开始。

## 2. 状态链怎么来

一条消息在 cc-web 服务端记成一条记录（按用户隔离，持久化在 `<dataDir>/<uid>/messages.json`）：

```
已发送 ──► 已送达(对方收到) ──► 等待对方批准 ──► 处理中 ──► 对方已空闲 ──► 已回复
  send        receive          (receive 后 N 秒      prompt.submit   Stop       对方 send
                                还没开始处理)          origin=peer               回给发送方
```

"等待对方批准"是推断的：收到了、但几秒内没开始处理，且对方不忙。推断可能误判（对方正忙时消息排队），卡片上写"未开始处理"而不是断言"被扣住"。

**线程化**：发送方的 mod 在正文末尾加一个不显眼的标记 `[ccw:t=<id>]`，接收方的 mod 在收到时把它剥掉并记下来；接收方回复同一个会话时，mod 自动把最近一个未结的线程标记加回去。这样"派了什么 / 回了什么"能串成一条线，模型看到的正文不变。

### 3.1 派活面板（发送方，任务菜单 → 派活…，或侧栏任务右键）

```
┌ 派活给其他任务 ─────────────────────────────── × ┐
│ 目标  [▾ 招标采购V2接收代理系统数据  PMS · 空闲 · Auto ] │
│        ├ cgs-master / 采购公告…        忙   · Default │
│        └ 同名任务会显示所在空间和创建时间                 │
│ ── 结构化（可选，填了就按模板拼成正文）──               │
│ 目标     [                                         ] │
│ 背景     [                                         ] │
│ 改动点   [ src/x.java:120  …                       ] │
│ 验收     [                                         ] │
│ 回复要求 [ 做完回我：改了哪些文件、怎么验证的       ] │
│ ── 或直接粘贴正文 ─────────────────────────────────  │
│ [                                                  ] │
│ [√] 对方空闲时提醒我                                  │
│                       [复制为提示词]  [取消]  [发送] │

```

发送不经过网页直发：网页把内容交给**发送方自己的 Claude**（作为一条用户输入，"请用 SendMessage 发给 X：…"），所以权限、审批都还是 Claude 自己的流程，网页不绕过任何东西。

### 3.2 消息卡片（双方都能看到同一张，在终端上方的一条消息栏 + 侧栏角标）

发送方：
```
┌ ↗ 派给「招标采购V2接收代理系统数据」 14:02 ─────────────┐
│ 修 PMS 两处公告标题…（展开看全文）                       │
│ ● 已发送 ● 已送达 ◐ 对方未开始处理（可能在等批准）        │
│                                    [跳到对方] [复制为提示词] │
│  └ ↩ 回复 14:31  已改 2 个文件，验证…  (展开)            │
└──────────────────────────────────────────────────────────┘
```

接收方：
```
┌ ↘ 来自「采购公告要展示公告标题」 14:02 ──────────────────┐
│ 全文可展开；文件:行号可点，直接在文件浏览器打开            │
│ 若终端里在等你批准：请在下方终端里批准 / 拒绝              │
│                                         [定位到终端提示]  │
└──────────────────────────────────────────────────────────┘
```

接收方的批准按钮**放在接收方自己的终端里**（Claude 原生的批准提示），网页只负责把人带过去、给出全文。发送方看到的永远只是状态和"跳到对方"，没有任何批准入口。

### 3.3 完成提醒

对方空闲或回复时：侧栏发送方任务上出现角标（同现有 ✓ / 待批准 标记的做法），页面不在前台时发浏览器通知，前台时出一个 toast，点击跳到线程。

### 3.4 兜底

卡片上"复制为提示词"：把正文连同"来自 X 会话，做完请回复"一起复制，送不到时用户手动粘到对方终端。

## 4. 需要用户决定

1. **给 cc-web 启动的每个 Claude 加载一个 cc-web 自带的 mod**（随仓库发布在 `mods/ccweb-companion/`，启动时用 `--plugin-dir` 传入）。这是整套功能的前提；mod 只观察消息、给正文加/剥线程标记，不替任何人批准。同意吗？
2. **批准留在终端里**（推荐）——网页不提供"批准 / 拒绝 / 以后都允许"按钮，因为 mod 接口做不到、硬发按键又容易按错。可接受吗？
3. **派活面板发送走"交给发送方自己的 Claude 去发"**，而不是网页直接发。好处是不绕过权限；代价是要多一步模型回合。同意吗？
4. 第一期范围建议：消息记录 + 状态链 + 双方卡片 + 线程 + 完成提醒 + 复制为提示词；派活面板的结构化模板放第二期。可以吗？

## 5. 实施前要先实测的

- 被扣住的消息在接收方是否触发任何钩子（Notification 等）——有的话"等待批准"就不用推断。另一条路：SendMessage 的说明写明，本机会话扣住或拒收消息时，发送方会收到一条 `[Cross-session delivery notice]`，空闲订阅到期或触发时会收到 `[Cross-session idle notice]`。这两条通知应能在发送方的 `session.receive` 里认出来，直接给出"被扣住 / 被拒 / 已空闲"，不用推断。
- `session.receive` 的 `text` 是否带发送方名字/地址（用于把回复路由回原线程）。
- `--plugin-dir` 加载的 mod 在 Windows 的 node-pty 启动方式下能否正常热加载、出错时是否影响 Claude 启动（不能影响）。

## 6. 定稿（2026-11-11 实施）

用户四项决定：①默认加载 mod；②批准留在接收方终端；③派活交给发送方自己的 Claude 发；④一期范围按推荐。上面第 4 节的问题都已按这四项定下。

### 实测结论（Claude Code 2.1.319，临时实例 32354，两个 haiku 会话）

| 问题 | 结论 |
|---|---|
| `--plugin-dir` 加载 mod | 正常加载；mod 目录或清单缺失时 cc-web 不传这个参数，Claude 照常启动 |
| 接收方 `session.receive` 的 text | 带着外层 `<cross-session-message from="uds:…" from-name="…" from-mode="…">`，线程标记在包裹内；mod 剥标记、server 解析 from 地址 |
| 回复怎么寻址 | 接收方 Claude 回复时 `to` 用的是 from 的管道地址，不是名字 → 按 `fromAddress` 认回复，实测挂回原线程 |
| idle / delivery 通知 | **不走** `session.receive`，而是作为一条 prompt（origin `unclassified`）到达发送方 → mod 在 `prompt.submit` 里识别 |
| 被扣住的通知 | 文字取自本会话真实收到的一条；第一句"was held by that session"，后文提到 "release, denial or expiry"，所以只按第一句判断 |
| 端到端 | 从 "Hand off to…" 弹窗派活 → 对方处理 → 回复：卡片依次走完 Sent → Delivered → Working → Idle → Replied，回复挂在原卡片下，发送方任务出现 Hand-off 标记、页头角标 1，打开抽屉后清零；接收方看到 "↘ From uiA" 和 Show terminal / Go to sender；手机 390 宽抽屉满屏、无横向溢出 |

### 没有实测到的

- **真实的"被扣住→批准→放行"**：要让两个会话的权限模式不同，需要用跳过权限的模式启动测试会话，被本会话的安全检查拦下了（没有绕过）。扣住通知的识别有单元测试（用真实措辞），拒绝的措辞已用真实通知核对（"was denied by the recipient user"，2026-11-11）；放行/过期的措辞仍是按 Claude 的说明推测的（released / expired），首次遇到真实通知时应核对一次 `peer-threads.json` 里线程的 `notices`。
